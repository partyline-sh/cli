# Partyline mobile

Expo 58 / React Native 0.88 / TypeScript. The native UI is bundled with the app;
the relay transports encrypted messages. No Partyline account or Face ID sign-in is required.

The iOS/Android provider uses the live runtime. Web uses explicitly labelled fixture
data for interface development. Pairing uses the camera screen (or pasted link),
Noise IKpsk2 and computer approval; only then are credentials saved to SecureStore.
Transport uses fresh KK handshakes and closes when the app backgrounds, then
reconnects and requests fresh snapshots on resume. Unknown inputs are never
replayed automatically and require a warning before retrying.

The runtime is tested independently of the screens. Android emulator checks cover
navigation, camera permission, invalid pairing input and process restart. Real-phone
QR pairing, Keychain and paired-session lifecycle behavior still require verification.
## Run

```sh
cd mobile
npm ci
npm start
npm run ios       # local iOS development build; Xcode and CocoaPods required
npm run android   # local Android development build; Android SDK/JDK required
```

Development builds are the target, rather than relying on Expo Go. Native project
directories are generated by Expo and ignored. Signing and physical-device
installation are separate from JS bundle export. iOS beta builds are distributed
through TestFlight invitations; an Android development build is not a Play Store
release. Use local signing credentials or the maintainer's distribution process;
no private team or signing key is committed here. The browser preview uses example
data and does not validate real-device pairing or native secure storage.

The user guide is [Mobile remote](https://partyline.sh/docs/mobile-remote). It covers
client choice, relay hosting, updates, pairing, storage and troubleshooting.

## UI contract

`src/runtime/types.ts` defines the public contract. Import `usePartyline()` and
`paneKey()` from `src/runtime`; a single provider owns the controller across all
routes. Secrets and sockets stay outside the UI. `fixture-controller.tsx` provides
example data with the same controller shape; it never uses the network.
`PartylineProvider mode="fixture"` can select it explicitly for UI development.

- `src/app/`: thin Expo Router wrappers.
- `src/ui/`: Claude's screens and custom tab bar.
- `src/runtime/`: Codex's controller, pairing, storage, connection and input logic.
- `src/ui/index.tsx`: exports consumed by the wrappers; `SessionScreen` receives
  `{ computer: string, pane: string }`.

Tool status may be absent; display an unknown status neutrally. Do not infer
success. Loop sections preserve the machine's names, including unrecognised
columns. Structured answer buttons are intentionally unsupported.

Runtime delivery behavior: identical pending text/paste/chat drafts
return their existing delivery, repeated keys remain separate, reconnect never
replays input, and unknown retries require a duplicate-execution warning.

## File and image attachments

Chat and session composers offer **Attach** for a photo or file, up to 20 MiB.
The paired computer must advertise the `uploads` capability. OS pickers provide
access only to the chosen item; attaching a photo does not request camera or
microphone access. The QR scanner still uses its existing camera permission.

The phone transfers bytes through the existing encrypted connection, with a
SHA-256 digest and at most four acknowledged 32 KiB chunks pending. Only a
confirmed finish adds the computer's absolute file path to the latest draft,
preserving edits made during transfer. The person still presses Send. A quoted
path is a reference for the receiving agent to read; this is not an inline image
rendered to everyone in Chat. Binary contents are not saved in the input queue.

Navigation, backgrounding, cancellation or a disconnected transfer stops the
upload without automatic retry or sending text. Re-select the file to retry.
The computer stores files in its private upload cache and may remove old files
to enforce its per-phone storage limit. Drafts retain paths, not copies of files.
Picker/transfer errors appear beside the composer. Fixture mode does not upload.

## Terminal and loop views

All LLM sessions share one **Simple / Session** selector and composer. **Simple**
shows the native conversation for Claude and Codex when it is available. If there
is no transcript reader or no conversation has been located yet, it shows confirmed
messages sent from this phone and explains that replies appear in **Session**.
Terminal screen text is never attributed to an assistant as a fake transcript.
**Session** always wraps text to the phone width while preserving the computer's
terminal size. Agent screens have no resize, exact-grid or fit-width controls.

Plain shells retain their separate terminal component. Its display defaults to
**Exact grid**; **Wrap text** reflows text locally and **Fit width** scales the grid.
For these shells, **Resize shared session** is an explicit opt-in and requires `terminal_resize`. It
resizes the shared terminal, including the computer's view, using the phone viewport
and font metrics. It renews every 10 seconds and releases when the terminal loses
focus, closes, or switches back to Desktop. The computer restores its previous size
and window-size policy; disconnected clients lose their resize lease after 30 seconds.
Split windows and windows held by another phone are refused. Earlier shell scrollback
retains its original wrapping; redrawing terminal apps can reflow to the new size.

Loops stage chips are independent checkboxes. Choose several stages to see their
cards together, grouped by stage. **All** follows newly added stages too. Explicit
stage selections remain selected when their last card moves elsewhere.


Bundle export validates Metro/Hermes compilation, not native binaries or device

Protocol adapters live under `src/runtime/protocol/`: Noise is copied unchanged
from the relay and tested against the same independent Go vectors. The session
adapter changes lifecycle ownership and base64 decoding for native. Pairing link
derivation and four-digit codes are pinned to the Go pairing vectors.
No terminal output or transcripts are persisted to device storage. Pairing secrets
are in SecureStore; selection, drafts and pending command identities use AsyncStorage.

An unsigned iOS simulator build, including SVG icons, compiled and launched on
iPhone 17 Pro / iOS 26.5 with Xcode 27.2. The live controller rendered the unpaired

The separate terminal parser regressions preserve selected-menu backgrounds,

To run the standalone Android smoke checks on a fresh, booted emulator:

```sh
python3 scripts/smoke-android.py --serial emulator-5582 \
  --apk android/app/build/outputs/apk/release/app-release.apk
```

## App Store artwork

The phone silhouette in `assets/partyline-mark.svg` comes from the existing web
brand mark. `npm run store:assets -- --apply-icon` renders three 1024px icon
options and applies the spectrum treatment to the app icon, adaptive layers,
splash image and favicon. Screenshot compositions use the terminal wordmark's
amber/pink/magenta palette. A new app build is needed to change the store icon.

Native captures use fictional workspaces and the real UI. The preview is enabled
only in debug builds with `EXPO_PUBLIC_PARTYLINE_SCREENSHOTS=1`; release builds
keep the live controller even if that environment variable is set. Do not capture
a live user's sessions or pairing codes for store images.

Start an isolated Metro instance:

```sh
EXPO_PUBLIC_PARTYLINE_SCREENSHOTS=1 npm start -- --dev-client --localhost --port 8084
```

With a debug app installed on a booted simulator (replace the explicit UUID):

```sh
xcrun simctl launch --terminate-running-process SIMULATOR_UUID sh.partyline.mobile \
  --initialUrl 'http://localhost:8084?__expo_disable_fab=1&__expo_disable_onboarding=1'
python3 scripts/capture-store-ios.py --device SIMULATOR_UUID
npm run store:assets
```

The capture script briefly selects each screen using `src/preview/target.json`,
restarts the debug app, captures it with simctl, and restores the original target
file. It does not clear app data or open the simulator viewer. Inspect captures
for developer overlays before sharing. Output is under ignored
`artifacts/store-assets/`: upload the PNGs in `iphone-medium/` (1206×2622) and
`iphone-large/` (1320×2868) to the matching App Store Connect slots. All composed
screenshots and store icons are opaque PNGs. Only the explicit store capture hides
the development example-data notice; ordinary fixture previews keep that notice
and the controller still reports fixture mode. To recapture one screen, pass
`--screens sessions` to the capture script.

[Apple screenshot specifications](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications/)
were checked on 2026-10-30; the medium Dynamic Island slot is required.

## Computers and private gateways

Computers groups saved pairings by their exact HTTPS relay address. Updated
computers report their configured hosting type inside the encrypted phone channel;
the phone saves that label for later visits. Older computers remain usable under a
generic Relay heading. The phone never changes its connection address from this
metadata, and never infers a provider from the hostname.

Expand a computer to reconnect, pair again after revocation, or forget its local
pairing with confirmation. Offline details show the last received message when
known; they do not diagnose sleep, VPN status or gateway failure. Group counts
refer to paired computers. No gateway roster or unpaired computers are exposed.

## Loop card details

Tap a loop card to see its untruncated summary, stage/state, batch step, round,
builder, reported checks/reviewers, open P1 count, dispute, pull request number
and CI status. The screen follows that loop on that computer as it moves between
stages. It labels missing fields as unreported and disconnected snapshots as
potentially out of date. Returning to the board retains its selected stage filters.

With a computer advertising `loop_controls`, the card also loads the complete brief,
configured checks and reviewers, baseline output, every round's check output and
findings (including P2/P3), builder reports and batch summary. Details over 512 KiB are refused explicitly and need the computer; they
are never truncated into a partial approval brief. Refresh requests a
fresh copy. A pull-request URL can be opened on the phone.

Available controls follow the live state: approve a brief, request changes with a
note, require a disputed finding's fix or dismiss it, reverse the next standing
arbiter dismissal, resume a paused review, stop the loop/batch, or permanently
delete the loop/batch. Each asks the computer for a five-minute, one-use challenge
bound to this phone, action and exact loop/brief/dispute/batch snapshot. The phone
shows what will happen and a four-digit code the person must type. The computer
checks it under the run lock and audits the phone, gate and choice before acting.
A changed brief/revision/finding refuses the action. Delete names the entire batch
when the loop belongs to one. There is no phone-decision CLI or HTTP endpoint.

Effects use the same persisted request IDs and delivery states as typing. They are
never replayed automatically after disconnect/reload. Unknown delivery blocks the
next action on that loop or shell creation until the person checks and retries the
same request (with a duplicate-execution warning) or acknowledges it. A process
restart invalidates outstanding loop challenges. Older computers keep the board
summary and show an update hint instead of controls.

## Opening a shell

In Sessions, **New terminal** under a connected computer opens an ordinary shell
window in that computer's Partyline tmux session, starting in the computer user's
home directory. It appears alongside the agent sessions and uses the existing
terminal view, input keys, wrapping and delivery confirmations. Leaving the phone
does not close it; use `exit` in the shell when finished. The `shell_open` capability
is required; older computers show an update hint. No arbitrary startup command or
path is accepted over this operation.

Shells use a local command line instead of the agent message composer. Type a command
and press Return (Go on the phone keyboard) to run it. Edits stay on the phone until
submission; Return on an empty field sends Enter to the remote shell. Pasted multiple
lines require confirmation before running. Autocorrection, capitalization, spellcheck
and smart spacing are disabled; commands are not rewritten or sanitized.

For shell completion, type a partial command, tap **insert**, then **tab**. Insert
pastes without Enter and clears the matching draft only after confirmation. The key
strip sends keys to the remote program, not the local field. This is a command entry
field, not per-keystroke typing for interactive editors. **file** opens attachments;
uploads add a quoted path to the local draft without running it. Normal confirmations
appear as an inline tick; refusals, uncertain delivery and Retry remain visible.

**Display** reveals text size, wrapping, Fit width and shared-resize options. Hiding
these options retains the chosen display mode and any active resize lease. A shared
resize stays visible with a Restore action. Unknown font glyphs remain unchanged;
this update does not bundle a Nerd Font.

## State indicators

Sessions show terminal-style work meters only while their computer is connected and the session
reports working. Waiting and idle are still, and a disconnected computer replaces the cached
session badge with Offline. Connection packets move only while connecting or reconnecting.
Delivery packets mean the phone is awaiting computer confirmation; a still check appears only
when that confirmation arrives. Unknown delivery retains the existing warnings and retry rules.

Loop cards show Build, Checks and Review from reported states and check/reviewer chips. Tap the
card, then a stage to inspect its reported details. A check means finished, not necessarily passed;
missing results remain unreported. Disconnected and paused snapshots do not animate.

Motion uses native transforms and opacity, stops when its route loses focus or the app backgrounds,
and follows changes to the system Reduce Motion setting. Text and still symbols preserve the same
status when motion is disabled. No timing-based progress percentages or extra network polling are used.

## Delivery and room activity

Send waits for the computer to send Enter before confirming. On computers advertising
`input_feedback`, a later observation reports the agent working, an identifiable unchanged draft
still in the input box, or plain delivery when application state cannot be determined. Working
is an observed session state, not proof that a particular message has been answered. A new draft
is never cleared by that observation. Unknown delivery retains the existing duplicate-execution warning.

Agent feedback also checks the native conversation against a prompt baseline recorded before
sending. A new matching user entry followed by assistant text shows **Answered** when idle,
including turns that finish before the working-state observation; ongoing replies show
**Reply arriving**. Prior identical prompts, stale snapshots, tool-only entries and an idle pane
alone do not prove an answer. Engines without conversation data direct readers to Session.
This uses existing transcript updates and the bounded local input history; it adds no polling.

Retry Enter references the original input; it never resends its text. The computer checks the
phone, authorized pane identity, two-minute expiry, and unchanged recognized composer snapshot
before pressing Enter. Changed or ambiguous drafts refuse the shortcut. Wrapped, multiline and
collapsed drafts may remain plain Delivered because their content cannot be verified safely.

Chat keeps Posted to room visible after confirmation. Its activity panel uses the existing encrypted
room membership and session reports to distinguish working, reply pending, input needed, unread
messages and paused chat. Pausing chat does not stop a session doing other work. Disconnects clear
live room activity. Older computers without the metadata show activity unavailable; no model
thinking state is invented from a transport receipt. These indicators add no snapshot polling.

### Chat formatting and mentions

Room messages render bold, lists, fenced code and small tables using native text/views. Code
and tables scroll horizontally within the message on narrow screens. Raw HTML and image
references remain text; chat does not run HTML, fetch images or open links. Very large messages
fall back to selectable plain text. Reading older messages does not force the scroll to the end.

Type `@` in the room composer to filter the selected computer's live room members. Tap a member
ID or engine token to insert it at the caret without sending. Engine tokens may address several
members; their labels show the count. Dismissal preserves the draft. Suggestions disappear when
room metadata is unavailable. Direct terminal input and the delivery protocol are unchanged.

## Direct shell terminal (build 15)

A computer advertising `live_terminal` uses the bundled xterm WebView for direct
cursor input in native shell sessions. Older computers, agent sessions and web
retain the existing composer. Live keystrokes never enter the persistent input
queue. Backgrounding, disconnect, overflow and refusals discard pending input.

The protocol, scope, prediction rules, sampling budget and measured limitations
are in `../docs/plans/mobile-live-terminal.md`. After editing browser.ts or
prediction.ts, install mobile and relay dependencies and run `npm run terminal:bundle`.
The generated offline document and xterm MIT license are checked in deliberately.

## Streaming phone terminals

With a computer advertising `term_stream`, **New terminal** opens a phone-owned shell with no desktop window. Input and output use an ordered byte stream through the existing paired encrypted connection. Output is parsed incrementally by bundled xterm.js; it does not use screen polling. Existing desktop sessions keep their previous viewer/input path. Older computers expose an explicitly labelled legacy terminal.

Phone terminals are listed below the computer's New terminal action. Reopen one to reconnect; choose **End** and confirm to terminate its shell and running commands. Backgrounding or losing a connection discards pending input and detaches the client while the shell keeps running. Reconnect starts a fresh attachment and lets tmux redraw its terminal state. Output stays visible while disconnected. Detached sessions expire after 24 hours; at most eight are retained per computer. The desktop launcher lists them as Phone terminal (list-only); `x` opens an explicit End confirmation rather than trashing a transcript.

The backend uses a separate tmux server derived from the normal socket plus `-phone`, with prefixes, mouse bindings and status disabled. `github.com/creack/pty` supplies the real PTY required by the tmux client. Input/output frames bypass the snapshot ticker. Output batches for up to 8 ms, with 16 KiB chunks and a 256 KiB parse-ACK window. These are implementation bounds, not a measured device latency guarantee.

`npm run test:terminal` checks both legacy predictive rendering and the streaming renderer, including split UTF-8, parser ACK ordering, application-mode cursor keys and retained output after disconnect. Physical-phone latency, IME and keyboard behavior still require device validation.
